# 完整论文生产

按已经选择的中心故事和目标作者档案写作。用户要求整篇时，持续写到完整初稿。

## 总体规则

- 一节只承担它在全文论证中的职责。
- 一段只推进一个主要信息。
- 图表承载证据密度，正文解释问题、模式和意义。
- 章节顺序服从目标 venue；写作顺序可以与最终阅读顺序不同。
- 保留用户现有引用键、公式符号、图表标签和文件格式。

## Method

从 baseline 和用户代码恢复方法，不按代码文件顺序写。

推荐动作：

1. 定义任务、符号和必要前提；
2. 用最短篇幅交代 baseline 或标准流程；
3. 给出统一方法思想和整体数据流；
4. 依照依赖关系介绍核心组件；
5. 解释组件如何共同实现中心创新；
6. 给出训练目标、算法或推理过程；
7. 将实现细节放到适合的位置，不让其遮住方法概念。

每个核心组件都应回答：为什么需要、接收什么、执行什么、输出什么、如何进入整体方法。公式用于明确关系，不用于替代解释。

## Experiments / Results

先提出研究问题，再选择支撑它的表和图。常见顺序：

```text
实验设置
→ RQ1 整体方法是否有效
→ RQ2 效果在哪些任务或条件下成立
→ RQ3 核心组件是否必要
→ RQ4 为什么有效、何时失效或有何权衡
```

对每组结果采用：

```text
问题
→ 比较设计
→ 最重要观察
→ 跨行列模式
→ 对中心故事的意义
```

正文只强调最能支持局部结论的数字。表中已有的密集数值无需逐一复述。结果弱于 baseline 时，明确条件并判断它是否形成真实权衡或收缩适用范围；不要用措辞把劣势改写成优势。

消融实验必须对应具体设计主张。容量、参数量、训练预算或其他因素混杂时，描述观察到的变化，不把它归因于单一机制。

## Related Work

Related Work 的组织轴来自本文中心创新，而不是年份或作者列表。

1. 从 baseline 论文及其引用建立起点；
2. 搜索 baseline 发表后的最新近邻工作；
3. 按技术问题或方法路线分组；
4. 每组说明已经解决什么、仍留下什么、与本文是什么关系；
5. 结尾给出本文准确位置。

不要从标题或搜索摘要猜论文贡献。引用前阅读原文或可靠的完整摘要与方法描述，并记录来源。避免把多个文献句子拼接成一段。

## Introduction

在 Method、Experiments 和文献位置稳定后反推 Introduction：

```text
实验共同建立了什么
→ 方法解决了什么具体问题
→ baseline 为什么受到这个问题限制
→ 现有工作为何仍留下这个位置
→ 该问题为什么值得解决
```

再按照目标作者档案选择段落动作。一个常见但非强制的序列是：

```text
任务与价值
→ 主流路线
→ 具体限制
→ 核心观察
→ 方法概览
→ 主要结果
→ 贡献
```

贡献围绕研究主张组织。方法组件只有在各自代表独立思想或发现时才分别列为贡献。

## Discussion / Conclusion

目标 venue 有独立 Discussion 时，回答：主要结果共同说明什么、为什么可能如此、对领域理解有何影响、适用条件是什么。机制尚未由实验直接建立时，将其作为解释或假设，而不是 Results 的重复。

Conclusion 用最短路径收束：问题、方法思想、核心结果和意义。不要引入正文没有建立的新应用和新贡献。

## Abstract

最后写 Abstract：

```text
具体问题
→ 未解决位置
→ 方法思想
→ 两到三个主要结果
→ 对任务或领域的意义
```

压缩论证链，不机械压缩各章节。不塞入所有数据集、baseline、指标和模块名称。

## Title

从最终中心故事产生标题。优先表达研究问题、核心思想或主要发现；只有方法名称本身就是主要贡献时才把缩写放在最前。

## 写作期间的轻量对齐

每节完成后只问：

1. 它在回答中心问题的哪一部分？
2. 它使用了哪些真实材料？
3. 它怎样把读者带到下一节？

发现偏离时当场重写，不累积到最终润色阶段。
